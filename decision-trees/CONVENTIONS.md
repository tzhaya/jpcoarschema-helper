# フローチャート共通規約

同じ要件でも、ページごとに説明の順序や言葉が変わると、入力者は規則そのものが違うように感じます。
とくに、スキーマの公式定義、DOI登録時の要件、本ガイドの判断基準が一つの段落に混ざると、どこまでが必須なのか追えません。

`decision-trees/` 配下の入力ガイドは、[title.md](title.md) の構成を基準とし、このファイルの凡例、用語、方針に従います。
共通事項は各ページへ再掲せず、必要な箇所から本ファイルを参照してください。

---

## 1. ページ構成

入力者は、最初に項目の性質をつかみ、フローチャートで判断し、対応表と入力例で値を確定します。
最後に注記へ戻れば、判断の根拠を3層別に確認できます。

各ページは次の順で構成します。

1. **見出しと導入**：入力時に迷う点を具体的に示し、このページで確定する判断を述べる
2. **対象と典拠**：対象要素、公式定義のまとめ、DOI対照表へのリンクを示す
3. **要素の要点**：記入レベルと繰返回数を、公式記号と作業上の意味を併記して示す
4. **この項目の性質**：入力作業を4観点で評価する（第8節）
5. **まず入力するもの**：代表的な値と入力先を早見表で示す
6. **記号凡例**：本ファイルへの参照だけを置く
7. **入力フローチャート**：Mermaid の `flowchart TD` で判断順を示す
8. **入力プロセス対応表**：フローチャートの各判断を、質問、回答、処理、要素、入力例へ対応づける
9. **使い分けの目安**：迷いやすい境界事例を比較する
10. **入力例**：代表的な完成形を XML で示す
11. **注記（入力ルール）**：スキーマ層、DOI登録層、本ガイドの運用方針に分けて根拠を示す
12. **参考**：公式ページ、[要素別ルール](../reference/)、[DOI対照表](../reference/JPCOAR_JaLC_Crossref_requirements.md)を示す

### 各節の役割

同じ規則を複数の節で説明し直しません。
必要な情報は、読者がその時点で行う作業に合わせて配置します。

| 節 | 担当する内容 | 書かない内容 |
|----|--------------|--------------|
| 導入 | 何に迷うか、何を決めるページか | 項目一覧やページ構成の予告 |
| まず入力するもの | 代表的な値から入力先を引く早見表 | 詳細な典拠説明 |
| フローチャート | 判断の順序と到達先 | 長い例外説明 |
| 対応表 | 図のノードと実際の要素、属性、値の対応 | 図にない独立ルール |
| 使い分けの目安 | 境界事例の比較 | 全語彙の網羅的な再掲 |
| 入力例 | 判断後の完成形 | 新しいルール |
| 注記 | 判断の根拠と例外 | フローチャートの進行実況 |

導入は「このページでは何を扱う」とだけ宣言せず、対象項目で実際に起きる迷いから始めます。
たとえばタイトルなら、別言語の代表タイトル、副題、シリーズ名で入力先が変わる事実を先に置きます。

## 2. 記号凡例（Mermaid）

| 記号 | 意味 |
|------|------|
| 楕円 `([ ])` | 開始または終了 |
| ひし形 `{ }` | 判断（Yes / No や種類の分岐） |
| 長方形 `[ ]` | 処理（入力または設定する内容） |
| 平行四辺形 `[/ /]` | 入力または情報源 |

各ページの「記号凡例」には表を再掲せず、次の1文を置きます。

```markdown
記号・記入レベル（M / MA 等）・`xml:lang` 運用方針は [CONVENTIONS.md](CONVENTIONS.md) を参照してください。
```

## 3. スキーマ層の記号

公式記号だけでは、入力者が取るべき行動が見えにくい場合があります。
各入力ガイドでは記号を残し、作業上の意味を併記します。

| 記号 | 厳密な意味 | 入力時の言い換え | 注意 |
|------|------------|------------------|------|
| M | 必須（Mandatory） | 必ず記載 | 省略できません |
| MA | 該当する場合は必須（Mandatory if Applicable） | 条件に当てはまる場合は記載 | 何が条件かを本文で具体的に示します |
| R | 推奨（Recommended） | できれば記載 | 省略は可能ですが、記載が望ましい項目です |
| 1-N | 1回以上、繰返可 | 1つ以上記載、複数可 | 少なくとも1つ必要です |
| 0-N | 0回以上、繰返可（必須以外） | あれば記載、繰り返し可 | ない場合は省略できます |
| 0-1 | 0〜1回、繰返不可（必須以外） | あれば1つだけ記載 | 複数は記載できません |

要素の要点では、`title.md` と同じく記号と作業上の意味を一続きで示します。

```markdown
`dc:title` は **M（必須）、1-N（1つ以上、繰返可）** です。
```

## 4. DOI登録層の用語

[JPCOAR/JaLC対照表](../reference/JPCOAR_JaLC_Crossref_requirements.md) は、「任意」と「推奨」を項目ごとに使い分けています。
入力ガイドでも、次の用語を原文どおり使用します。

| 用語 | 意味 |
|------|------|
| **必須** | 必ず入力が必要 |
| **条件付必須** | 特定条件下で必須（例: 親要素がある場合） |
| **任意** | 入力は任意（0以上 または 0〜1） |
| **推奨** | 任意だが入力が推奨される |

タイトルの `xml:lang` は JaLC DOI で**任意**、作成者名の `xml:lang` は**推奨**です。
どちらも省略可能ですが、同じ語へ言い換えることはできません。

作業上の説明が必要な場合は、「任意（あれば記載）」のように正式語を残して補足します。

## 5. 3層の原則（最重要）

同じ属性に、スキーマ、DOI登録、本ガイドから別々の要件が加わることがあります。
たとえばタイトルの `xml:lang` は、スキーマ上は MA、JaLC DOI では任意、Crossref DOI では必須です。
本ガイドは、さらに原則付与を求めます。

三つを一文にまとめず、次の層を区別します。

| 層 | 典拠 | 例 |
|----|------|----|
| **スキーマ層** | [公式説明ページ](https://schema.irdb.nii.ac.jp/ja/schema) と [要素別ルール](../reference/) | `dc:title` は M、1-N。`xml:lang` は MA |
| **DOI登録層** | [対照表](../reference/JPCOAR_JaLC_Crossref_requirements.md) | タイトル `xml:lang` は JaLC＝任意 / Crossref＝必須 |
| **本ガイド運用方針** | 本ファイル | `xml:lang` は入力漏れ防止のため原則付与 |

### 根拠の強さを本文で示す

同じ「〜します」で書かれていても、公式に規定がある記述と、本ガイドが判断した記述では、入力者が従うべき度合いが違います。
公式規定と同じ書き方で解釈を述べると、読者はその判断を公式要件として受け取ります。

根拠の強さに応じて、次のように書き分けます。

| 根拠 | 本文での書き方 | 例 |
|------|----------------|----|
| 公式資料に規定がある | 通常の記述。出典を「参考」または注記で示す | 「学位論文では、作成者を必ず記載します」 |
| 公式資料からの推論を含む | 解釈であることを示す | 「本ガイドでは、翻訳者を寄与者として扱うと解釈します」 |
| 公式に規定がなく本ガイドが定めた | 運用方針であることを示す | 「本ガイドの運用上、標題紙で一体の副題は `dc:title` に含めます」 |
| 根拠を確認できない | 原則として記載しない | ― |

根拠を確認できない記述は、原則として `decision-trees/` と `reference/` の本文に置きません。
判断の材料として残す場合は、未確認であることと、確認できていない範囲を明記します。

「多い」「多数」のような頻度や数量の主張も、出典を示せない場合は記述に含めません。
かわりに、入力者が確認できる条件や手順を書きます。

公式に規定がない判断へ「公式準拠」「スキーマの規定により」といった表現は使いません。

### 根拠の強さと3層は別の軸

この節は二つの軸を扱います。
**層**は要件がどこから来るかを示し、**根拠の強さ**はその記述をどこまで断定できるかを示します。
二つは直交するため、DOI登録層にも解釈は生じます。

解釈と運用方針にも、対応する層があります。
注記では層ごとの小見出しをそのまま使い、その中で「〜と解釈します」「本ガイドの運用上」と書き分けます。
解釈のための小見出しを新設しません。

### 点検作業の分類は本文に持ち込まない

既存ページの記載を根拠別に棚卸しする際は、公式明示・解釈・運用方針・根拠未確認といった区分を作業用に使います。
この区分は点検一覧の中だけで用い、`decision-trees/` と `reference/` の本文には記号として現れません。
読者に対しては、前項の書き分けだけで根拠の強さを示します。

### 注記の標準形式

各ページの「注記（入力ルール）」は、次の小見出しに分けます。

```markdown
## 注記（入力ルール）

### スキーマ層

（公式定義と `*_rules.md` に基づく規則）

### DOI登録層

（対照表に基づく登録先別の必須度。比較がある場合は表を使う）

### 本ガイドの運用方針

（入力漏れ防止、判断基準、推奨手順などの独自方針）
```

スキーマ層では、記入レベル、繰返回数、属性、統制語彙、公式の記述ルールを扱います。
DOI登録層では、登録先や資源タイプで変わる必須度を扱います。
本ガイドの運用方針では、公式が詳細を定めていない境界の判断や、作業上の推奨を扱います。

登録先ごとの差が二つ以上ある場合は、文章を連ねず比較表にします。

## 6. `xml:lang` の運用方針

`xml:lang` の要件は要素と登録先によって変わるため、「Crossref なら常に英語必須」のように一般化できません。
各ページでは対象要素の対照表を確認し、3層別に記載します。

- **スキーマ層**：該当する場合は必須（MA）
- **DOI登録層**：要素と登録先ごとに異なる。JaLC DOI は任意または推奨、Crossref DOI は必須となる要素が多い。一部の要素では `xml:lang="en"` も必須
- **本ガイドの運用方針**：入力漏れと多言語の混在を防ぐため、原則としてすべての言語依存値に付与する
- **1言語につき1要素**：一つの要素に複数の言語を並べず、言語ごとに要素を分ける

### 言語コード

| 用途 | コード例 |
|------|---------|
| 日本語、英語、中国語（簡体） | `ja` / `en` / `zh-cn` |
| 片仮名ヨミ | `ja-Kana` |
| ローマ字ヨミ | `ja-Latn` |

ヨミ（`ja-Kana` または `ja-Latn`）を入れる場合は、本文言語（通常は `ja`）の値も併記します。

## 7. 用語

用語は、フローチャートと対応表で同じ判断を指すために使います。
公式にない概念を設ける場合は、「運用上の区分」または「本ガイドの運用方針」と明記します。

| 用語 | 定義 |
|------|------|
| 並列タイトル | 同一資源の代表タイトルが複数言語で示されたもの。`dc:title` を言語別に繰り返す |
| その他のタイトル | 本タイトル以外のタイトル。独立した副題、目次タイトル、奥付タイトルなどを `dcterms:alternative` に記載する |
| ヨミ | 読みの情報。`ja-Kana` または `ja-Latn` を使用する |

用語はプロパティの追加に応じて追記します。

## 8. 項目の性質（評価の物差し）

転記だけで決まる項目と、資料の解釈や外部調査を要する項目では、入力者が注意を向ける場所が違います。
各ページの冒頭に「この項目の性質」を置き、入力作業を次の4観点で評価します。

| 観点 | 問い | 記載する値 |
|------|------|-----------|
| **入力の型** | 何を行う作業か | **解釈型**（資料の性質を解釈して統制語彙などから選ぶ）、**転記型**（書誌や資料からの転記が中心）、**調査型**（外部情報源を調べて値を得る）。複合する場合は、どの部分がどの型かを添える |
| **他項目への影響** | この項目の選択が他項目の必須度や値を変えるか | **与える影響はあり／なし**を明記し、波及先を示す。他項目から影響を受ける場合も条件を記す |
| **事前調査** | 入力前に外部を調べる必要があるか | **必要／不要**を明記する。必要な場合は情報源や検索ツールを示す |
| **誤入力の影響** | 間違えると何が起きるか | DOI登録エラー、検索と発見性の低下、著者や資源の同定不能など、具体的な実害を示す |

### 記入フォーマット

```markdown
## この項目の性質

| 観点 | 評価 |
|------|------|
| 入力の型 | **転記型**が中心。資料に表示された値を写す。入力先を決める部分は解釈を伴う |
| 他項目への影響 | **与える影響はなし**。資源タイプの影響を受け、特定の条件では追加値が必須になる |
| 事前調査 | 不要。標題紙、奥付、書誌情報から判断できる |
| 誤入力の影響 | 検索と発見性の低下。必須値が欠けると DOI 登録エラーになる |
```

### 運用

- **解釈型**では、迷いやすい境界をフローチャートと「使い分けの目安」の両方で扱います。
- **転記型**では、早見表と対応表から値を確定できる構成を優先します。
- **調査型**では、検索先やデータベースへの導線を「参考」に置きます。
- 4観点は [ROADMAP](../ROADMAP.md) の優先度判断にも使います。
- この評価は本ガイドの運用上の目安であり、公式スキーマの規定ではありません。

## 9. フローチャートと対応表

フローチャートは、入力者が実際に判断する順序を示します。
公式要素の階層をそのまま図に写すものではありません。

- Mermaid は `flowchart TD` を使用します。
- 開始点は、原則として `資源／登録する文献` とします。
- DOI要件が変わる項目では、上流に「DOI登録先は?」を置きます。
- 資源タイプによって要件が変わる場合は、DOI登録先の後に資源タイプ分岐を置きます。
- 判断ノードには入力者が答えられる質問を書き、要素名だけを置きません。
- ノード内の説明は判断に必要な範囲に絞ります。典拠、例外、長い語彙一覧は注記または対応表へ移します。
- 公式が定めていない判断基準を図へ入れる場合は、「本ガイドの運用上の判断」と明記します。
- 実在しないページへリンクしません。後続ページが未作成の場合は「（作成予定）」と記載します。

フローチャートの直後には、分岐全体を理解するための短い「判断の要点」を置くことができます。
図の内容を順番に言い直すのではなく、入力先や必須度を変える条件を一つに絞って示します。

```markdown
> **判断の要点**：本タイトルの入力先は DOI 登録先によって変わりません。
> 変わるのは `xml:lang` の必須度です。
```

対応表の行はフローチャートの判断番号と一致させます。
図にない規則を対応表だけへ追加すると判断経路を追えなくなるため、追加の規則は注記へ置きます。

## 10. 使い分けと入力例

「使い分けの目安」は、似た値を比較し、どの事実で入力先が変わるかを示す節です。
単なる語彙一覧にはしません。

表の前に、判断軸を一段落で示します。
たとえばタイトルでは、言語の違いよりも、その文字列が資料を代表しているかどうかが入力先を決めます。

| 列 | 内容 |
|----|------|
| 迷いやすいケース | 入力者が実際に遭遇する資料上の状況 |
| 判断 | 入力先を決める分類または条件 |
| 入力先 | 要素、属性、または別項目への誘導 |

入力例は、フローチャートと対応表で確定した規則の完成形を示します。
入力例の節で新しい条件や例外を導入しません。

- 単純な例から始め、並列値、下位要素、境界事例の順に複雑にします。
- 見出しは「例1」のような番号ではなく、「日本語タイトルのみ」「独立した副題」のように内容を示します。
- 一つのコードブロックには、一つの判断結果を示します。
- XML は要素名、属性、値を確認できる最小限の形にします。

## 11. 文体と表記

入力ガイドは参照資料ですが、規則の羅列だけでは判断の違いが見えません。
導入と節の間には、対象の性質から生じる疑問や差分を置き、読者が次に確認する理由を保ちます。

本文は、執筆時から `japanese-tech-writing` に従って書きます。
新規作成と大規模改訂では、最終段階で `cognitive-rhythm-writing` を導入と注記に適用します。
軽微な修正では、独立した推敲工程を省略できます。
スキルの保存場所は実行環境によって異なるため、この規約ではスキル名だけを指定します。

- 一文ごとに改行し、話題が変わる位置で空行を置きます。
- 冒頭はページ構成の予告ではなく、入力時に起きる具体的な迷いから始めます。
- 「ここでは」「次に」「まとめると」など、文書の進行だけを述べる文は置きません。
- 同じ規則を早見表、対応表、注記で言い換えて繰り返しません。
- 太字は記入レベル、判断の対比、誤読を防ぐ語に限ります。
- 日本語の並列には中黒やスラッシュを多用せず、読点または「と」「または」を使います。要素名、コード、公式の表記は変更しません。
- DOI登録層の「必須」「条件付必須」「任意」「推奨」は言い換えません。
- 確認できない解釈を公式要件として断定しません。独自の判断は本ガイドの運用方針として示します。

推敲は文章表現を整える工程です。
公式定義、記入レベル、DOI要件、Mermaidの分岐、対応表、XML例の意味を変更する工程ではありません。
推敲で変更した文は、対になる `reference/*_rules.md` とDOI要件の対照表に再度照合します。
変更していない箇所の再照合は不要です。
